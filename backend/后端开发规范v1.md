# 四川飞豹后端开发规范 v1

本文档基于当前仓库 `backend/` 的实际实现整理，目标是统一新增代码写法，并逐步收敛已有遗留模块。

## 1. 适用范围

- 适用于 `backend/src/` 下所有 NestJS 后端代码
- 适用于新增模块、接口、DTO、实体、鉴权、异常、响应封装
- 对历史遗留代码采用渐进式治理，不要求一次性重写

## 2. 技术栈基线

- 框架：NestJS
- ORM：TypeORM
- 数据库：MySQL
- 认证：JWT + Passport
- 文档：Swagger
- 参数校验：class-validator + class-transformer

## 3. 目录规范

### 3.1 业务模块

所有业务代码放在 `backend/src/modules/` 下，按业务划分模块，例如：

```text
backend/src/modules/news/
backend/src/modules/auth/
backend/src/modules/personnel/
```

### 3.2 公共能力

公共逻辑统一放在 `backend/src/common/` 下，例如：

- `guards/`
- `filters/`
- `interceptors/`
- `decorators/`
- `dto/`

### 3.3 实体位置

- 通用实体优先放 `backend/src/database/entities/`
- 仅当前模块使用的实体可以放模块内 `entities/`
- 同一张表只保留一个有效实体定义，避免重复实体并存

## 4. 分层规范

后端统一采用：

```text
Controller -> Service -> Repository
```

### 4.1 Controller 职责

- 定义路由
- 接收参数
- 挂认证、权限、Swagger 装饰器
- 调用 Service
- 返回业务结果

### 4.2 Service 职责

- 编排业务逻辑
- 访问 Repository
- 做业务校验
- 抛出业务异常

### 4.3 禁止事项

- 禁止在 Controller 中直接注入 `Repository`
- 禁止在 Controller 中直接写数据库 CRUD
- 禁止在 Controller 中手写分散的异常输出格式

## 5. 路由规范

- 全局前缀统一为 `/api`
- 路径命名保持资源化和可读性
- 优先使用 REST 风格

示例：

- `GET /api/news`
- `GET /api/news/:id`
- `POST /api/news`
- `PATCH /api/news/:id`
- `DELETE /api/news/:id`

## 6. 鉴权与权限规范

### 6.1 默认私有

项目默认由全局 JWT 守卫保护，新增接口默认需要登录。

### 6.2 公开接口

公开接口必须显式加 `@Public()`，例如登录、注册、前台公开查询接口。

### 6.3 权限接口

后台管理接口应显式声明权限：

```ts
@RequirePermissions('News')
```

### 6.4 认证文档

需要登录的接口应补：

```ts
@ApiBearerAuth()
```

## 7. DTO 与参数校验规范

### 7.1 必须使用 DTO

- `@Body()` 参数必须使用 DTO
- `@Query()` 参数优先使用 DTO
- 禁止新增 `@Body() data: any`

### 7.2 校验规则

DTO 使用：

- `class-validator`
- `class-transformer`

常用规则：

- `@IsString()`
- `@IsInt()`
- `@IsOptional()`
- `@IsNotEmpty()`
- `@Min()`
- `@Max()`
- `@Type(() => Number)`

### 7.3 依赖的全局能力

项目已启用全局 `ValidationPipe`，并启用了：

- `whitelist`
- `transform`
- `forbidNonWhitelisted`

因此 DTO 中未声明的字段应视为非法输入。

## 8. 响应规范

### 8.1 统一响应结构

统一响应结构为：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": 1234567890
}
```

### 8.2 实施规则

- Controller 优先直接返回业务数据
- 统一由全局 `TransformInterceptor` 包装为 `ResponseDto.success(...)`
- 仅在明确需要时手动返回 `ResponseDto`

### 8.3 禁止事项

- 禁止新增手写的零散 `{ code, message, data }` 返回格式
- 禁止同一模块混用多套响应结构

## 9. 分页规范

分页查询统一使用分页 DTO，至少包含：

- `page`
- `pageSize`

分页响应统一包含：

- `items`
- `total`
- `page`
- `pageSize`
- `totalPages`

推荐直接返回 `PaginatedResponseDto<T>`。

## 10. 异常处理规范

### 10.1 统一异常出口

项目统一通过全局异常过滤器输出错误响应。

### 10.2 业务中应抛标准异常

优先使用 Nest 标准异常，例如：

- `BadRequestException`
- `UnauthorizedException`
- `ForbiddenException`
- `NotFoundException`
- `ConflictException`
- `InternalServerErrorException`

### 10.3 禁止事项

- 禁止返回随意拼接的错误 JSON
- 禁止吞掉异常后返回模糊成功结果

## 11. 数据访问规范

- 使用 `TypeOrmModule.forFeature([Entity])` 注入实体
- 使用 `@InjectRepository(Entity)` 注入仓库
- 仓库只在 Service 内使用
- 查询条件、分页、排序统一收敛到 Service

## 12. Swagger 规范

新增接口必须补 Swagger 元信息：

- Controller：`@ApiTags`
- 接口：`@ApiOperation`
- 认证接口：`@ApiBearerAuth`
- DTO 字段：`@ApiProperty`

Swagger 文档不是补充材料，而是当前接口契约的一部分。

## 13. 配置规范

所有环境配置统一走 `ConfigModule` 和环境变量。

禁止：

- 在业务代码中硬编码数据库配置
- 在 Service/Controller 中硬编码端口、账号、密码、域名

## 14. 命名规范

- 模块：`XxxModule`
- 服务：`XxxService`
- 控制器：`XxxController`
- DTO：`xxx.dto.ts`
- 实体：`xxx.entity.ts`
- 装饰器：`xxx.decorator.ts`
- 守卫：`xxx.guard.ts`
- 过滤器：`xxx.filter.ts`
- 拦截器：`xxx.interceptor.ts`

## 15. 历史遗留治理原则

当前仓库存在以下遗留写法：

- Controller 直接操作 Repository
- 局部接口手写响应结构
- 个别接口仍使用 `any` 接收请求体
- 同一业务存在重复实体定义

治理原则：

- 新功能不再延续旧写法
- 修改旧模块时顺手向规范收敛
- 不做与当前需求无关的大面积重构

## 16. 新接口最小交付标准

新增一个后端接口，至少需要满足：

1. 路由放到对应业务模块
2. DTO 完整定义并启用校验
3. Controller 不直接访问 Repository
4. Service 承载业务逻辑
5. 接口具备鉴权或显式公开声明
6. 返回值符合统一响应规范
7. 异常走统一过滤器
8. Swagger 注解完整

## 17. 当前示范模块

`backend/src/modules/news/` 已开始按本规范收敛，可作为后续新增模块的参考起点。
